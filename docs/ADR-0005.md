# ADR-0005: Local locking and optimistic revisions; no distributed coordination

Date: 2026-11-07
Status: ACCEPTED (limits documented; distributed coordination out of scope for v1.0 per INTENTS.md)

## Context

Several agents may write at once on one machine (tested with 6 processes), or from different Git worktrees/machines.

## Decision

- One store-wide lock: `.handoffs/.write.lock` created with `O_CREAT|O_EXCL` (works on Windows and POSIX), 4 s wait, released in `finally`. It records `pid=... time=...`. A stale lock is **reported** (error text, `doctor`) and removed only by a human.
- Updates of an existing session need `--id` plus `--expected-revision` (compare-and-swap on `revision`); a stale writer fails with `Revision conflict` and nothing is saved.
- New sessions get unique ids (UTC timestamp + 12 hex) and are created with exclusive `mkdir`; metadata is written via temp file + `fsync` + `os.replace`.
- Archive/restore rewrite metadata, then rename; an interruption leaves a state `doctor` detects and a repeated command heals (`docs/RECOVERY_PROTOCOL.md`).
- Different worktrees have separate stores (`list --all-worktrees` reads them read-only). Merging them is a Git/PR concern; atomic rename is not claimed to solve distributed merge conflicts.

## Alternatives rejected

- OS advisory locks (`fcntl`/`msvcrt`): different semantics on Windows/NFS and no help across machines.
- Auto-breaking stale locks by pid liveness: pid reuse and cross-host locks make it unsafe.

## Consequences

- A crashed writer can block others (for at most manual intervention); acceptable because data loss is worse than a blocked write.
- Real kill/power-loss durability and network filesystems are untested (`docs/RELEASE_GATES.md`).
